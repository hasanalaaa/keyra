## 0. Findings in one page

1. **The premise "iOS will not let third-party managers receive Save prompts" is out of date.** Since **iOS 26.2** an AutoFill credential provider can implement `prepareInterface(for: ASSavePasswordRequest)` and `performWithoutUserInteractionIfPossible(savePasswordRequest:)`, plus `ASGeneratePasswordsRequest` for sign-up password generation ([Apple: ASCredentialProviderViewController](https://developer.apple.com/tutorials/data/documentation/authenticationservices/ascredentialproviderviewcontroller.md), [ASSavePasswordRequest](https://developer.apple.com/tutorials/data/documentation/authenticationservices/assavepasswordrequest.md)). Bitwarden is implementing it now ([Bitwarden forum](https://community.bitwarden.com/t/support-ios-26-2-password-generation-and-save-password-apis/96773)). So "Save to Keyra" in native iPhone apps and Safari is technically feasible, but only on iOS 26.2 or newer and only with a **paid** Apple Developer account ([Apple DTS](https://developer.apple.com/forums/thread/655154)).
2. **Android has had it since 8.0** (`AutofillService.onSaveRequest`, [Android docs](https://developer.android.com/identity/autofill/autofill-services)), and Android 14 adds a Credential Manager provider API for passkeys ([Android docs](https://developer.android.com/identity/sign-in/credential-provider)). Android is the easy platform and sideloading still works for a hobbyist (limited-distribution accounts launched August 2026) ([Android Authority](https://www.androidauthority.com/android-sideloading-changes-timeline-3679204/)).
3. **A phone app can be a "remote signer" front-end for a hardware key** and this is proven: Yubico's Passkey Enabler and the MIT-licensed Authnkey are Android credential providers that sign with an external FIDO2 key ([Yubico](https://docs.yubico.com/software/applications/yubikey-passkey-enabler/overview.html), [F-Droid](https://f-droid.org/packages/pl.lebihan.authnkey)). That is the only realistic way Keyra gets passkeys onto phones, because **BLE FIDO is dead** (not supported on iOS, macOS, Android or ChromeOS; removed from Chrome) ([Microsoft Entra matrix](https://learn.microsoft.com/en-us/entra/identity/authentication/concept-fido2-compatibility), [Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/3911741/is-ble-transport-for-fido2-roaming-authenticator-o)).
4. **USB FIDO2 on ESP32-S3 is feasible; the license is the trap.** Pico-Fido (the only ESP32-S3 implementation with a real feature set) is AGPLv3 with a separate commercial license ([picokeys](https://github.com/polhenarejos/pico-fido)). Permissive options exist (LionKey MIT, Solo 1 Apache-2.0/MIT, OpenSK Apache-2.0, OpenKey-Fido2 MIT/Apache) but none is a drop-in for ESP32-S3 (see P01).
5. **Without a secure element, the single most valuable security upgrade is not FIDO, it is a device-bound key.** ESP32-S3 can hold a read-protected eFuse HMAC key that software can use but never read ([ESP-IDF HMAC](https://docs.espressif.com/projects/esp-idf/en/v6.0.2/esp32s3/api-reference/peripherals/hmac.html)). Mixing that into the vault key wrapping turns a stolen flash dump from "guess the passphrase offline" into "also needs this one chip". It changes the persisted vault format, so the wrap structure must be decided **now** (H11, Wave D1).
6. **2026's real new battleground is AI agents.** 1Password (Secure Agentic Autofill) and Bitwarden (Agent Access SDK, Apache-2.0) both ship "agent asks, human approves, credential injected without entering the model's context" ([1Password](https://1password.com/blog/closing-the-credential-risk-gap-for-browser-use-ai-agents), [Bitwarden](https://bitwarden.com/blog/introducing-agent-access-sdk/)). Keyra's button-gated keystroke injection is a natural physical version of that. Nobody has built it on hardware (M08).
7. **Several popular features are impossible or dishonest offline and are rejected here:** emergency access with a wait period, dead-man switch, tamper wipe (see section 5).
8. **Keyboard layout cannot be read from the device side.** USB HID has no layout channel; the HID country code is not acted on by any OS ([forum summary](https://forum.arduino.cc/t/keyboard-layout-automatically/906762)). The only honest sources of truth are the user (R1 N7 Layout Doctor) or the Companion extension in the browser (`navigator.keyboard.getLayoutMap()`, Chromium-only) (H09).

## 1. "Save to Keyra" inside native iPhone and Android apps

### 1.1 What iOS actually allows (as of 2026-10-07)

All rows are from Apple's own documentation for `ASCredentialProviderViewController` unless another link is given ([source page](https://developer.apple.com/tutorials/data/documentation/authenticationservices/ascredentialproviderviewcontroller.md)).

|---|---|---|---|

Hard limits that no API removes:

- The extension runs only when iOS invokes it for an AutoFill operation; it cannot run in the background or refresh the identity store on a schedule ([panicvault](https://www.panicvault.org/apple/credential-provider-extensions/)). A save request arrives with a short-lived UI; if Keyra is unreachable at that moment the password is not saved unless the extension holds it somewhere (see 1.4).
- Extensions have stricter memory limits than apps and Apple controls how QuickType suggestions look ([panicvault](https://www.panicvault.org/apple/credential-provider-extensions/)).
- Some apps use custom text views that do not take part in AutoFill at all ([panicvault](https://www.panicvault.org/apple/credential-provider-extensions/)). Nothing Keyra does fixes that.
- **Adoption reality:** 1Password deliberately does not implement the *silent* save, only a consent prompt ([1Password community](https://www.1password.community/lounge-50/ios-26-2-autosave-incorporation-possibility-24150)). Bitwarden has separate PRs for the silent path and the with-UI path ([Bitwarden forum](https://community.bitwarden.com/t/support-ios-26-2-password-generation-and-save-password-apis/96773)). For Keyra, always show UI and require the button (consent plus physical presence), never use the silent path.
- Whether a save request goes to Keyra when the user also has Apple Passwords or another provider enabled is not documented in what I could read **[verify on device]**.

Honest verdict on the premise: it is no longer impossible; it is **iOS 26.2+ only**, so iPhones that cannot or will not update stay on the web app plus BLE typing.

Practical meaning: a Keyra iOS app is **a $99-class commitment per year (price not re-verified here) plus a TestFlight or App Store process**. For an open-source MIT hardware project, the owner has to decide whether to run one publisher account for everyone (TestFlight link, 90-day rebuild cycle) or tell makers to build the app themselves with their own paid account. Networking constraints specific to Keyra (Keyra serves plain HTTP on a no-internet AP):

- iOS 14+ shows a Local Network permission prompt and requires `NSLocalNetworkUsageDescription`; Bonjour browsing needs declared `NSBonjourServices` ([OWASP MASTG](https://mas.owasp.org/MASTG/knowledge/ios/MASVS-PLATFORM/MASTG-KNOW-0128/)). Whether an AutoFill **extension** gets its own prompt or inherits the app's is not documented in what I read **[verify]**.
- Cleartext HTTP to `*.local` and unqualified hosts needs `NSAllowsLocalNetworking`; it removes ATS enhanced requirements for local connections only ([Apple forum](https://developer.apple.com/forums/thread/6205)). Raw IPs such as `192.168.4.1` and ATS are a separate, historically confusing case **[verify]**; prefer `keyra.local`.
- Programmatic join of Keyra's AP uses `NEHotspotConfiguration` (needs the Hotspot Configuration entitlement, which is "unmanaged": no special Apple approval but a paid account) ([Apple forum](https://developer.apple.com/forums/thread/703017)). **Use `joinOnce = true`**: Apple DTS says `joinOnce = false` makes iOS treat the accessory network as a saved one and it may drop it mid-session for a saved internet network ([Apple forum](https://developer.apple.com/forums/thread/848895)).
- The much simpler and more robust path is **home Wi-Fi mode** (SPEC §8.2): both Keyra and the phone are on the same LAN with internet. A passkey or sign-up flow needs the phone to have internet anyway; on Keyra's own AP it would rely on cellular fallback.

### 1.4 Architecture for a minimal native "Keyra" companion app

Design rules (these keep the project's promise intact):

1. **The app stores no secrets.** Nothing in the app sandbox that decrypts to a password: no cached vault, no master passphrase, no token that lets a thief list entries without Keyra.
2. **Keyra authorises by physical press, as everywhere else.** A save is an **add** request that Keyra confirms with the button; a fill is armed and released by the button.
3. **Credentials flow in two directions with different risk.**
   - *Phone to Keyra (save, generate)*: the password already exists on the phone (the user typed it or the OS generated it). Sending it to Keyra only reduces exposure. Safe by design.
   - *Keyra to phone (fill)*: three modes, decided per user:
     - **Mode A, default, no secret on the phone:** the app arms Keyra's pending action and Keyra **types over BLE HID** (SPEC §8.1) into the phone's focused field. The app is only a remote control. Caveats: a BLE keyboard hides the on-screen keyboard on iOS and BLE layouts are the R1 P1 pain point; Mooltipass users report an iOS custom-keyboard conflict ([minible #215](https://github.com/mooltipass/minible/issues/215)).
     - **Mode B, opt-in, "return the credential":** after the press, Keyra sends the username/password to the extension/service which hands it to the OS fill API (`provideCredential...` on iOS, `Dataset` on Android). The secret transits the phone's RAM for milliseconds. That is the same exposure as the Copy button already in the web app (R1 F52) but through the OS autofill pipe. Must be labelled honestly in the UI and README.
     - **Mode C, passkeys via remote signer:** see 2.4.

**iOS app** (SwiftUI app + Credential Provider extension target, both with the `autofill-credential-provider` entitlement):

| Piece | Responsibility |
|---|---|
| `ASCredentialProviderViewController` subclass | `prepareInterface(for: ASSavePasswordRequest)`: show a Keyra-styled sheet ("Save to Keyra?", title, username, masked password, **Save / Not now**), POST to Keyra (`/api/ext/save` equivalent from SPEC §9.4, same server contract as the browser Companion), then show "Press Keyra's button", wait for result, call `completeSavePasswordRequest`. |
| Same class | `prepareInterface(for: ASGeneratePasswordsRequest)`: pass the rules to a Keyra endpoint (`POST /api/generate` already accepts length/classes/symbol set; add a rules parser or send the Apple rules string) so the generated password is hardware-random. |
| Same class | `prepareCredentialList` / `prepareInterfaceToProvideCredential`: list matches from `POST /api/ext/match {host}` (no secrets), arm, then Mode A or B. Never use `provideCredentialWithoutUserInteraction` for passwords (it cannot wait for a button). |
| Transport | `URLSession` to `http://keyra.local` or the stored home-LAN address; pairing is the Companion's presence-gated bearer token (SPEC §9.4) kept in the **Keychain with a biometric/passcode access control** so the token alone is not enough on a stolen unlocked phone. Needs `NSLocalNetworkUsageDescription`, `NSBonjourServices`, ATS local-networking exception. |
| Memory | Hold nothing; wipe the save request's password from memory right after the POST. |
| Settings screen in the app | Pair, forget, mode A/B, "enable in Settings" button via `ASSettingsHelper` ([Apple](https://developer.apple.com/tutorials/data/documentation/authenticationservices/ascredentialproviderviewcontroller.md)). |

Also: the same app container is what lets Keyra ship a **Safari Web Extension on iOS** (Companion for iPhone Safari), which otherwise needs an app host **[verify]**.

**Android app** (Kotlin, minSdk 26 for Autofill, 34 for passkey provider):

| Piece | Responsibility |
|---|---|
| `AutofillService` | `onFillRequest`: identify the app package or web domain, return a `FillResponse` that has an **authentication action** (an Activity: "Press Keyra's button") rather than datasets, plus `SaveInfo` (username + password ids). `onSaveRequest`: read the structure, POST to Keyra, show a heads-up "Press Keyra's button to save". |

| Passkeys | `CredentialProviderService` for Mode C (2.4). |

Recommended path: **write a small CTAP2 core in C++ under MIT**, using TinyCBOR (MIT) plus mbedTLS (already in ESP-IDF) for ES256, referencing LionKey and Solo 1 for behaviour (with attribution where code ideas are taken), and test it with `fido2-tests` / ctap2-test-tool. Do not start from Pico-Fido.

### 2.2 What it takes on ESP32-S3 USB

- **Endpoint budget.** The S3's USB-OTG block is limited to 6 endpoints (5 bidirectional + 1 IN) according to a component README that summarises the TRM ([espp usb_device](https://components.espressif.com/components/espp/usb_device/versions/1.3.0/readme)) **[verify whether EP0 is counted]**. Keyra today uses HID keyboard (1 IN) plus, in dev builds, CDC (3). A FIDO HID interface needs IN + OUT. Release builds (no CDC) fit; dev builds with CDC are tight. The same README says the composable `espp::UsbDevice` approach takes an application-supplied report descriptor per HID function, so a custom FIDO descriptor (usage page 0xF1D0, 64-byte reports) is supported by that component; whether the pinned `esp_tinyusb` on ESP-IDF 6.0 does the same is R1 open item 4.6 **[verify]**.
- **PIN and user verification.** Microsoft Entra requires user verification for MFA and says security-key registration "doesn't work" on some macOS/iOS browsers that do not prompt for a PIN ([Microsoft](https://learn.microsoft.com/en-us/entra/identity/authentication/concept-fido2-compatibility)). So a Keyra that only does "button = user presence" will be rejected by serious relying parties; it needs **CTAP2 ClientPIN**.
- **Attestation.** Without a secure element: **self attestation or none**. A relying party that insists on an attestation chain will refuse Keyra; one that only wants a credential accepts it. Yubico's guidance notes that with self/no attestation "no provenance information is provided" and RPs that want to restrict authenticators can only do so via attestation ([Yubico](https://developers.yubico.com/WebAuthn/Concepts/Securing_WebAuthn_with_Attestation.html)). Practical effect: consumer sites work; some corporate allow-lists will not.
- **Resident-key limits.** Hardware keys are capped: YubiKey 25 passkeys on firmware 5.0-5.6 and 100 on 5.7+ ([Yubico](https://support.yubico.com/hc/en-us/articles/360013790319-How-many-accounts-can-I-register-my-YubiKey-with)). Keyra's vault is a flash filesystem (at least about 1.5 MB per SPEC §7); one credential is a few hundred bytes **[verify]**, so thousands fit and the practical cap is the vault's entry count. Passkeys can live in the existing encrypted entry format (a new item type, R1 F21) and therefore **ride along in encrypted backups**, which hardware keys cannot (R1 P4, [MakeUseOf](https://www.makeuseof.com/passkeys-are-great-no-one-tells-you-about-catch-until-its-too-late/)). That is a genuine advantage and a genuine risk (see 2.6 on flags).
- **PIN = unlock.** CTAP ClientPIN lets the OS ask for a PIN in its own dialog. Keyra can accept the **master passphrase as the FIDO PIN** (it is longer than most PINs; the spec allows long PINs **[verify the max length and character rules]**), run the same PBKDF2 unlock, and so make "locked vault + FIDO request" a one-step flow from the computer with no phone. Without this, every passkey login while the vault is locked would require the phone first. **[design inference]**
- **Extensions worth doing:** `hmac-secret` (this is what `systemd-cryptenroll` LUKS unlock uses; Crypto-T-key-S3 documents it) and `credProtect`. Also: any FIDO2 authenticator with ECDSA-P256 can back OpenSSH `ecdsa-sk` keys, and resident keys can be generated with `ssh-keygen -O resident` ([OpenSSH 8.2 release](https://www.openssh.com/txt/release-8.2), [privsec guide](https://privsec.dev/posts/linux/securing-openssh-with-fido2/)). So CTAP2 gives Keyra **SSH and LUKS** with no host agent, which R1 F13/F14 had written off.

### 2.4 The phone route: Keyra as a remote signer behind a credential provider (new idea)

Precedent: Yubico's **Passkey Enabler** lets an Android phone use passkeys on a hardware key over USB/NFC and acts as a passkey provider service ([Yubico](https://docs.yubico.com/software/applications/yubikey-passkey-enabler/overview.html)); **Authnkey** (MIT, Android 14+) does the same via the Credential Provider API with PIN and fingerprint handling ([F-Droid](https://f-droid.org/packages/pl.lebihan.authnkey)). The Android provider API requires the provider to *produce* the signature, not to *hold* the key ([Android docs](https://developer.android.com/identity/sign-in/credential-provider)); that signature can be computed on an external device. iOS providers likewise return an assertion via `completeRegistrationRequest` / assertion completion ([Apple](https://developer.apple.com/tutorials/data/documentation/authenticationservices/ascredentialproviderviewcontroller/prepareinterface(forpasskeyregistration:).md)).

Sketch for Keyra: the app/extension receives the WebAuthn request (RP ID, challenge, calling origin), builds `authenticatorData || clientDataHash`, sends it to Keyra over Wi-Fi (`POST /api/passkey/sign`), the user presses the button, Keyra signs with the credential key that never leaves the device, the app returns the assertion. The same for registration: Keyra generates the key pair and returns the public key plus credential ID.

Honest risks:

- **Origin binding moves to the phone.** Keyra signs the hash it is given; it cannot independently check which site asked. Phishing resistance then depends on the phone OS's provider API delivering the right origin, exactly as for any software passkey provider. Weaker than a USB key (where the browser on the computer talks CTAP directly) but equal to today's phone providers. **[design inference]**
- **Transport.** Plain HTTP on the LAN means an on-path attacker could replay or relay a signing request; each request must be single-use, presence-gated, and bound to the session. This needs the encrypted-link design of R1 N3 (C2) before it ships. Do not do it over unauthenticated HTTP.
- It adds a Wi-Fi dependency to passkey login on the phone (home Wi-Fi mode strongly preferred, see 1.2).

### 4.5 Hardening that actually changes the threat model

R1 recommends documenting optional flash encryption and secure boot as irreversible steps (README "Security model" says the same). What round 2 adds:

- **Flash encryption in release mode** makes the dump useless without the eFuse key: the key is generated on device, write- and read-protected, and used only by hardware. Release mode disables UART-bootloader encryption operations and the key cannot be reprogrammed; OTA still works through `esp_partition_write` ([ESP-IDF flash encryption](https://docs.espressif.com/projects/esp-idf/en/v6.0.2/esp32s3/security/flash-encryption.html)). Cost for Keyra: the `tools/devctl.py` development flow (download mode and 1200-baud reset) changes; this is a **build profile for people who want it**.
- **Fault injection is a real, documented threat.** ESP32 v1 and v3 eFuse and AES protections were broken with fault injection ([Espressif advisory](https://espressif.com/en/news/Security_Advisory_Concerning_Fault_Injection_and_eFuse_Protections), [Black Hat 2022](https://infocondb.org/con/black-hat/black-hat-usa-2022/unlimited-results-breaking-firmware-encryption-of-esp32-v3)). For ESP32-S3, **AR2026-005 (2026-06-10)** reports AES key recovery on the *general-purpose AES peripheral* by voltage fault injection with differential fault analysis; Espressif says it is **distinct from the XTS-AES flash-encryption peripheral** and rates deployed impact **low** because it needs physical access, equipment and a located AES operation ([Espressif summary via search](https://documentation.espressif.com/AR2026-005_Security_Advisory_Concerning_AES_Key_Recovery_Using_Voltage_Fault_Injection_on%20ESP32-S3_EN.html)). Consequence for Keyra: do not claim hardware-grade protection; claim "raises the cost of an offline dump".
- **Device-bound wrap with the HMAC peripheral (the new idea).** The ESP32-S3 HMAC peripheral computes HMAC with a key held in an eFuse block (purpose `HMAC_UP`), which can be read-protected so the key "never leaves the hardware module", and software only gets the output ([ESP-IDF HMAC](https://docs.espressif.com/projects/esp-idf/en/v6.0.2/esp32s3/api-reference/peripherals/hmac.html)). If one wrap of the vault DEK uses `HMAC(device key, PBKDF2 output)`, a flash dump alone cannot be attacked offline even without flash encryption; the attacker must run guesses on the device, where Keyra's persisted counter and rate limit apply. This **does not depend on flash encryption**, so it works with the normal dev flow until the user burns the eFuse. **[design inference, not an Espressif-documented pattern; needs a design review]**
  - **Contract:** this means the vault meta stores a *list of wraps* of the same DEK (passphrase wrap, optional device-bound wrap, later recovery-key wrap from R1 F34 and R03). Landing that list shape now costs almost nothing; retrofitting after release breaks the persisted format. Backups must stay restorable with passphrase alone, so the device-bound wrap is **never the only wrap** and is not included in the backup file's key path.

## 5. Safety nets: lost device, recovery kits, heirs, dead-man switch

R1 B5 (recovery key) and C5 (Shamir shares and heir kit) cover the first half. This section settles what is feasible **offline**, with no server.

### 5.1 What users of other managers already get

- 1Password combines the account password with a random **Secret Key** held in the **Emergency Kit** and added **recovery codes** for the case where the password is forgotten or the kit is lost ([1Password](https://1password.com/blog/introducing-1password-recovery-codes)). Bitwarden says it cannot retrieve or reset a forgotten master password and its recovery code does not replace it ([summary](https://maketecheasier.com/mte-j-a-password-manager-stores-your-vault-in-the-cloud-as-encrypted-ciphertext-not-readable-passwords-which-is-why-recovery-must-be-set-up-before-you-forget-the-master-password/)). The design point from that comparison: what matters is **who held the recovery secret before access was lost** (same source).
- Bitwarden's emergency access is a **server workflow**: invitation with the contact's RSA public key, a request, a wait time of at least one day, owner can approve or deny, then View or Takeover ([Bitwarden](https://bitwarden.com/help/emergency-access/)).
- The cautionary tale for any "split key" feature: **Ledger Recover** (2023) split an encrypted seed into three Shamir shares held by Ledger and two partners and required ID; the backlash was about the key leaving the device and custodial shares, and Ledger postponed and open-sourced the protocol ([NFT Now](https://nftnow.com/features/ledger-recover-is-your-seed-phrase-really-safe/), [Globalsecuritymag](https://www.globalsecuritymag.fr/Shattered-Trust-Ledger-s-New-Recovery-Feature-Stirs-Up-Crypto-Security-Concerns.html)). Keyra's rule: **the owner holds every share; no vendor, no custodian, no ID.**

### 5.2 Feasibility, feature by feature

- Never put the DEK, a passphrase or a seed phrase into any **printed QR without a passphrase or share threshold**; a bare QR is a bearer secret.
- Recovery must be **tested at setup**: ask the user to type back the first and last group of the recovery key, as R1 B5's acceptance criteria already imply.
- Any feature that lets a third party reach the vault must show a plain-language warning in Arabic and English, because the owner may not read the English threat model.
